# MemOS × MemTrace 集成：产品功能说明

## 1. 概览

| 产品 | 一句话定位 | 归属 |
| --- | --- | --- |
| **本插件**（`memos_smartcomment`） | 面向开发者的调试工具。把每次记忆写入和检索都记录成一张执行图，记录本身不影响业务结果。 | MemOS 可选插件，默认关闭，按需开启 |
| **MemTrace** | 读取执行图，沿着数据依赖往回查，找出导致答案出错的那一步操作，并给出诊断报告。 | 浙大 ZJUNLP 开源项目，[独立仓库](https://github.com/zjunlp/MemTrace)，不随本插件提供 |
| **smartcomment** | 两者之间的「通用语言」，定义执行图的数据格式，负责导出 JSON 和可视化。 | 公开 PyPI 包，本插件的依赖 |

简单说，本插件负责记录，MemTrace 负责分析，smartcomment 是两者共用的数据格式。

### 1.1 定位：开发者内部迭代的调试工具

本插件服务于开发者的开发与调试。开发者在本地或测试环境中通过环境变量按需开启，用来排查 bad case、分析评测失败、验证改动效果。调试结束后关闭即可。使用 MemOS 的用户对它完全无感，生产部署也无需安装或开启。

| 关注点 | 说明 |
| --- | --- |
| 面向用户 | 开发者和算法 / 评测同学，用于内部迭代时定位问题。 |
| 使用场景 | 复现和排查 bad case、跑基准评测并做错误归因、验证提取 / 增强 / 检索策略的改动是否生效。 |
| 如何开启 | 启动服务前设置 `MEMOS_ENABLED_PLUGINS=smartcomment`。需要检索溯源时再加 `MEMOS_SMARTCOMMENT_LINK_SEARCH_TO_ADD=true`。不设置时插件不会加载，去掉变量后重启即关闭。 |
| 对用户的影响 | 无感。插件只旁路订阅 Hook，不改变任何请求、响应和业务结果，API 行为与未开启时完全一致。 |
| 生产部署 | 无需安装，也无需开启。线上服务保持默认配置即可，不会产生任何执行图文件或额外开销。 |

## 2. 要解决的问题

MemOS 回答错了，或者「应该记住的事没记住」，原因往往不在最后一步，而是藏在中间某个环节：

- **写入时**：MemReader 没有从对话里提取出这条事实；
- **后台增强时**：MemRead 调度器把记忆合并、改写或删除了；
- **检索时**：记忆其实还在，但被相关度阈值、去重或重排过滤掉了。

MemOS 的日志只能看到零散的事件，看不出「这条记忆从哪条消息来、经过了哪些步骤、在哪一步消失了」。本插件和 MemTrace 合在一起，目的是在开发调试阶段帮助开发者把这条链路看清楚。

## 3. 整体关系

```text
                    ┌──────────────────── 本插件负责 ────────────────────┐   ┌──────── MemTrace 负责 ────────┐
                    │                                                    │   │                               │
 ┌───────────┐ Hook │ ┌──────────────┐   ┌──────────────┐   ┌──────────┐ │   │ ┌───────────┐   ┌───────────┐ │
 │   MemOS   │ ───▶ │ │ 观测与快照    │ ─▶│ 建图与关联    │ ─▶│ 落盘与索引 │ │ ─▶│ │ 回溯探查   │ ─▶│ 归因与报告 │ │
 │ Add/Search│      │ └──────────────┘   └──────────────┘   └──────────┘ │   │ └───────────┘   └───────────┘ │
 └───────────┘      │                                                    │   │                               │
                    └──────────────────────────┬─────────────────────────┘   └───────────────▲───────────────┘
                                               │      graph.json（smartcomment 执行图格式）      │
                                               └────────────────────────────────────────────────┘
```

- **数据流方向是单向的**：MemOS → 本插件 → 执行图文件 → MemTrace。MemTrace 不会回写 MemOS，本插件也不会调用 MemTrace。
- **连接点只有一个**：本插件输出的 `graph.json`。它采用 smartcomment 格式，和 MemTrace 已支持的 Mem0、EverMemOS、RAG 等系统的执行图格式相同，所以 MemTrace 可以直接加载，不需要额外转换。
- **两者可以单独使用**：不装 MemTrace 时，本插件的产物也能直接查看、可视化或用脚本分析。

## 4. 本插件的功能

开发者开启插件后，它运行在 MemOS 服务进程内，通过 MemOS 已有的 Hook 机制工作，**不修改 MemOS 的任何业务代码**。以下功能都只在插件开启时生效。

### 4.1 记录写入链路

记录一次 `/product/add` 中，记忆从原始对话到写入存储的全过程：

```text
原始消息批次 ──提取──▶ 提取出的候选记忆 ──写入──▶ 已写入存储的记忆（带 memory_id）
```

功能：监测这批消息被提取成了哪几条记忆，每条记忆写入后的 ID 是什么，提取或写入有没有失败

### 4.2 记录后台增强

MemOS 的 MemRead 调度器会在请求返回**之后**继续异步处理记忆：精炼增强、写入增强结果、删除旧记忆。本插件把这些迟到的操作**追加到原来那张 Add 图上**，一张图就能看完一次写入的前因后果：

```text
已写入的记忆 ──增强──▶ 增强后的记忆 ──写入──▶ 新的已写入记忆
            └──删除──▶ 调度结果
```

功能：监测 MemRead 调度器将记忆后来被改成了什么

### 4.3 记录检索管线

记录一次 `/product/search` 的每个阶段，图中**只保留各阶段处理后仍存在的记忆列表**：

```text
查询 → 记忆类型 → cube → 原始召回 → 阈值过滤 → 去重 → 重排（最终结果）
```

功能：通过比较相邻阶段的结果列表，监测记忆有没有被召回、在哪个阶段消失，以及最终返回结果的顺序和分数。被剔除的记忆不再单独生成列表节点，阶段 metadata 保留过滤数量统计。结果列表的 category 按 raw、threshold、dedup、rerank 区分，DOT 图以不同颜色展示各阶段。

### 4.4 检索结果溯源

开启 `MEMOS_SMARTCOMMENT_LINK_SEARCH_TO_ADD=true` 后，本插件会把 Search 的最终结果**连回它们在历史 Add 图中的来源**，并把来源链路复制进这张 Search 图：

```text
原始消息批次 → 提取 → 写入 → 增强 → 写入 ◀──溯源── 最终检索结果
```

连接边由最终检索结果列表指向记忆单元，comment 展示该结果在列表内从 1 开始的 rank 和实际 score。这样只看一张 Search 图，就能知道「这条结果最初来自哪批消息、中间经历了什么」。

这是本插件最关键的产品能力：它把原本分散在多次请求里的写入图和检索图串成一条完整的证据链，MemTrace 拿到这张图后，可以从检索结果一路追溯到原始对话。

### 4.5 请求目录，开箱即读

输出文件按「用户 / 日期 / 请求类型」组织，每个用户自动生成一份 `index.md`，按时间倒序列出每次请求的类型、查询或消息摘要、trace ID 和图文件链接。不需要任何工具，打开 Markdown 就能找到想看的那次请求。

| 时间 | 类型 | 请求摘要 | Trace ID | 图 |
| --- | --- | --- | --- | --- |
| 2026-10-15T14:36:10+08:00 | search | 我什么时候去游泳？ | 462f7ef9... | graph |
| 2026-10-15T14:35:22+08:00 | add | 2 messages: 我上周开始学游泳了… | 0ba7563d... | graph |

通过请求头 `x-trace-id` 可以指定 trace ID，方便把执行图和业务日志对应起来。

### 4.6 可视化与脚本分析

本插件的产物是标准 smartcomment 执行图，因此可以直接使用 smartcomment 自带的能力：

- `smartcomment-visualize` 一键生成交互式 HTML、PNG 图片或 DOT 源文件；
- 用 `ExecNetwork` 写几行 Python，查询祖先 / 后代节点、按类别筛选，例如「这条消息最后变成了哪些记忆」「哪些记忆在去重阶段被剔除」。

> 严格来说，可视化和 `ExecNetwork` 是 **smartcomment 的能力**，本插件负责产出能被它们直接读取的文件。

### 4.7 调试时不干扰服务

本插件不面向生产部署，但开发者常常需要在接近真实的环境中复现问题。下面这些设计保证：即使在调试时开启插件，MemOS 的正常服务也不受影响。

| 特性 | 说明 |
| --- | --- |
| **默认关闭** | 安装后不会生效，必须显式设置 `MEMOS_ENABLED_PLUGINS=smartcomment` 才会启动插件，去掉后重启即可关闭。生产部署保持默认即可，无需任何额外配置。 |
| **非侵入** | 只订阅 Hook，不改变任何请求、响应和业务结果。插件出错不会影响 MemOS 请求，调用方对插件是否开启无感。 |
| **不阻塞请求** | Hook 中只做数据快照，建图、溯源和写文件都在后台线程完成。队列满时丢弃事件并告警，不会为了记录而拖慢业务。 |
| **可靠落盘** | 原子写文件，服务重启或缓存淘汰后，迟到的事件会从磁盘恢复，继续追加到原来那张图上。 |

## 5. MemTrace 中与本插件相关的功能

MemTrace 是一个完整的记忆系统错误分析框架，下面与本插件相关的能力由 MemTrace 提供，需要单独安装 [MemTrace 仓库](https://github.com/zjunlp/MemTrace)并配置 OpenAI 兼容的模型。本插件不包含也不修改 MemTrace 的任何功能。

### 5.1 共同基础：operation-variable 执行图

MemTrace 把记忆系统的运行过程表示为一张「操作—变量」执行图：**变量**是运行中产生的具体数据，**操作**是产生或使用这些数据的步骤，**边**表示数据依赖。答案出错时，沿着依赖往回追，就能找到错误是在哪一步引入的。

本插件就是按这套模型来记录 MemOS 的，两边的概念一一对应：

| MemTrace 概念 | 在本插件产物中的对应 |
| --- | --- |
| **变量** | 原始消息批次（`input_message_batch`）、提取出的记忆（`extracted_memory`）、已写入的记忆（`persisted_memory`）、增强后的记忆（`enhanced_memory`）、检索查询（`search_query`）、各阶段保留的检索结果列表（`search_memory_list_{stage}`） |
| **操作** | MemOS 中的提取、写入、后台增强、归档 / 删除、召回、阈值过滤、去重、重排，以及检索结果溯源，统一以 `memos.` 开头命名 |
| **依赖** | Add 内的「消息 → 提取 → 写入 → 增强」、Search 内的各阶段结果链，以及「最终检索结果 → 记忆单元」的溯源边；只记录确定的关系，不按时间先后猜测 |
| **说明文字** | 每个节点、边和操作都带一句英文 `comment`，MemTrace 探查时会展示给 Agent，帮助它理解每一步在做什么 |

因此，本插件输出的 `graph.json` 可以用 `ExecNetwork.import_graph()` 直接加载，这也是 MemTrace 内部读取执行图的同一个入口，不需要格式转换。

### 5.2 交互式图探查：可直接使用

这是 MemTrace 中与本插件结合最紧密的能力，由两个组件组成：

- **`GraphTraceNotebook`**：加载一张执行图，从指定的起点节点出发，向 Agent 提供「查看节点、展开上游 / 下游、查看操作」等图工具；
- **`GraphTraceAgent`**：一个 LLM Agent，根据你的问题调用这些工具逐步查看图，最后基于图中的证据给出结论。

用于本插件产物时：

| 环节 | 做法 |
| --- | --- |
| **选哪张图** | 推荐用**开启溯源后的 Search 图**。它同时包含检索的各个阶段和最终结果的 Add 来源，Agent 在一张图里就能从检索结果一路追到原始对话。不开溯源时 Search 图只有检索部分，Add 图只有写入部分，Agent 无法跨图回溯。 |
| **从哪里开始** | 怀疑「检索出了问题」时，以最终结果列表（`search_memory_list_rerank`）为起点；怀疑「某句话没记住」时，以对应的消息批次节点为起点。 |
| **怎么提问** | 告诉 Agent 预期答案，让它逐步检查相关消息有没有被提取、写入、增强，最终有没有被检索到，在哪个操作丢失了。 |
| **能得到什么** | 一个基于图中证据的结论，例如「该事实在 MemReader 提取时未被抽出」或「该记忆被召回，但在阈值过滤阶段被剔除」。 |

### 5.3 批量错误归因与诊断报告：需要补充问答数据

如果要分析的不是单个问题，而是一整轮评测中的大量失败用例，可以使用 MemTrace 的两个批量工具：

- **批量错误归因**（`run_error_attribution.py`）：对每个失败用例自动定位导致错误的关键操作，并判断错误类型；
- **诊断报告**（`generate_report.py`）：汇总所有归因结果，用 LLM 总结目标系统的常见失败模式，输出系统级报告。

这两个工具不能直接读取本插件的产物，原因是它们需要一张**完整的问答图**，即除了写入和检索，还要有问题、模型回答、标准答案和标注。本插件只记录 MemOS **服务端内**的写入和检索；「根据检索结果生成回答」通常发生在客户端或评测脚本中，因此不会出现在图里。

| 批量归因需要的内容 | 本插件是否提供 |
| --- | --- |
| 记忆写入、后台增强的执行过程 | ✅ Add 图 |
| 检索各阶段的执行过程与结果 | ✅ Search 图 |
| 检索结果到原始消息的依赖链 | ✅ 开启溯源后的 Search 图 |
| 问题、模型回答、标准答案、错误标注 | ❌ 需要在评测侧补充 |

也就是说，本插件提供了批量归因中最难获取的那部分数据，即 MemOS 内部的执行过程。剩下的问答数据需要和评测结果一起，整理成 MemTrace 批量工具要求的格式（MemTraceBench 格式）。

## 6. 典型使用场景

### 场景一：单个 bad case 排查（只用本插件）

> 用户说「我告诉过你我周二周四游泳」，MemOS 却答不上来。

1. 打开该用户的 `index.md`，找到那次 Search 和之前的 Add；
2. 看 Add 图：这句话有没有被提取成记忆？后台增强时有没有被删掉或改写？
3. 看 Search 图：这条记忆有没有被召回？是被阈值、去重还是重排剔除的？
4. 开启溯源（即 Add 和 Search 图相连）后，只看 Search 图就能把整条链路看全。

**价值**：几分钟内判断问题出在提取、增强还是检索，不用翻日志，也不用加调试代码。

### 场景二：AI 分析（本插件 + MemTrace Agent）

> 主要场景：链路很长、记忆很多，人工看图太累，使用 Agent 进行错误归因。

1. 本插件产出 Search 图（建议开启溯源）；
2. 用 MemTrace 的 `GraphTraceNotebook` 加载这张图，以最终检索结果或可疑的消息批次为起点；
3. 告诉 `GraphTraceAgent` 预期答案，让它逐步检查「相关消息有没有被提取、写入、最终检索到，是哪个操作丢掉的」。

**价值**：由 Agent 基于图中证据给出结论，适合复杂 case 或需要可解释结论的场合。

### 场景三：系统级评测与归因（本插件 + MemTrace 批量工具，需要额外整理数据）

> 在 LoCoMo 等基准上评测 MemOS，想知道失败主要集中在哪些环节。

1. 用独立的输出目录跑评测，本插件记录全部 Add / Search；
2. 在评测脚本中完成问答和打分，把失败用例的问题、答案、标注和对应执行图组织成 MemTraceBench 格式；
3. 运行 MemTrace 的批量归因，再用诊断报告汇总失败模式。

**价值**：从「某个 case 错了」上升到「MemOS 的哪个模块最常出错」，为优化提供方向。

## 7. 快速开始（开发 / 调试环境）

以下步骤只用于本地或测试环境的调试，生产部署请跳过。

```bash
# 1. 在运行 MemOS 的同一环境中安装
python -m pip install "smartcomment>=0.1.2"
python -m pip install -e apps/memtrace-memos-integration

# 2. 按需开启插件进行调试（必须在启动服务前设置；不设置则插件不加载）
export MEMOS_ENABLED_PLUGINS=smartcomment
export MEMOS_SMARTCOMMENT_OUTPUT_DIR="$PWD/.memos/memtrace"
export MEMOS_SMARTCOMMENT_LINK_SEARCH_TO_ADD=true   # 推荐：开启检索溯源
python -m uvicorn memos.api.server_api:app --host 127.0.0.1 --port 8000 --workers 1

# 3. 正常调用 /product/add 和 /product/search 后，查看请求目录
find .memos/memtrace -name index.md

# 4. 调试结束：取消环境变量后重启服务，即恢复为未开启插件的状态
unset MEMOS_ENABLED_PLUGINS
```
